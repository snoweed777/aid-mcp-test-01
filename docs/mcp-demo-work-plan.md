## 1. ログ方針（MCPサーバ実装時の要件）

**必須レベルの定義は仕様書セクション4.4（ロギング要件）に従う。** 以下は作業上の確認観点の列挙である。

実装・起動時は次を満たすこと。**次工程に進む前に、該当ログ行の有無を確認する。**

| 区分 | 出力内容（例） | 目的 |
|------|----------------|------|
| 起動 | UTC時刻、`LISTEN` アドレス・ポート、`employees.json` の絶対パス、読み込み成功件数 | バインドミス・パスミス検知 |
| リクエスト | 接続元IP、HTTPメソッド・パス、SSE接続開始/終了 | 外部到達・クライアント切り分け |
| ツール実行 | ツール名、引数（PIIはマスク可）、処理時間ms、成功/失敗 | デモ・障害再現 |
| エラー | 例外型、メッセージ、スタック（DEBUG時のみ可） | 一次切り分け |

起動オプション例（計画レベル・仕様 4.1 の `LOG_LEVEL` と同じ）:

- 既定: INFO 以上を標準出力
- 障害調査時のみ: `LOG_LEVEL=DEBUG`

**ゲート**: サーバ起動後（フェーズ2）、ログに `employees loaded: N records`（同等文言）があり `N≥1` であること。満たさなければ **G2 未達としてフェーズ3（外部到達）に進まない**。

## 2. フェーズ一覧と進行ゲート

```
フェーズ1 → [ゲートG1] → フェーズ2 → [G2] → …
```

いずれかのゲート失敗時は、以降のフェーズに進まず、セクション7「巻き戻し」を実施する。

| フェーズ | 内容 | ゲートID |
|----------|------|----------|
| 1 | 開発環境・ファイル配置 | G1 |
| 2 | MCPサーバ起動（ローカル疎通） | G2 |
| 3 | ネットワーク（SG/OSFW・外部curl） | G3 |
| 4 | Cursor MCP クライアント | G4 |
| 5 | AID 登録・スキャン | G5 |
| 6 | AID Gateway URL → Dify | G6 |

---

## フェーズ1：開発環境・ファイル配置

### 1.1 作業

1. `mcp-server/` に `requirements.txt`・`mcp_server.py`・`employees.json` があることを確認（構成は仕様書セクション5）。
2. 仮想環境推奨: `python3 -m venv .venv && source .venv/bin/activate`
3. `pip install -r requirements.txt`（ログにエラー・警告がないこと）

### 1.2 確認コマンド（例）

```bash
cd <REPO_ROOT>/mcp-server   # またはリポジトリルートから: cd mcp-server
python3 -c "import json; d=json.load(open('employees.json')); print('records', len(d))"
```

（`<REPO_ROOT>` は仕様書セクション5のとおり、クローン先のルートディレクトリ。）

期待: `records 20`（デモ本番想定。検証中は少数でも可）。失敗時は JSON 構文・パスを修正。

### ゲート G1

- [ ] `pip install` 成功
- [ ] `employees.json` がPythonで読める
- [ ] `mcp_server.py` にログ方針に沿う起動・読み込みログが出力される実装になっている（コードレビューで確認）

**G1未達 → フェーズ2へ進まない**

---

## フェーズ2：MCPサーバ起動（EC2ローカル疎通）

### 2.1 作業

1. ターミナルAでサーバ起動（仕様のコマンド。例: `0.0.0.0` とポート明示）。
2. ターミナルBで **ループバックのみ** 疎通確認。

### 2.2 確認コマンド（例・パスは実装に合わせて置換）

```bash
# ヘルスやルートがあれば
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8765/health
# SSEエンドポイントのオプション確認（実装依存）
curl -sS -N -H "Accept: text/event-stream" "http://127.0.0.1:8765/sse" --max-time 3 || true
```

### 2.3 ログ確認（ターミナルA）

- [ ] 起動ログに **`0.0.0.0:8765`**（または設定ポート）が表示されている
- [ ] **`127.0.0.1` のみ** になっていない
- [ ] 社員データ読み込み成功のログがある

### ゲート G2

- [ ] ローカル `curl` が想定どおり（HTTPコードまたはSSEの初回イベント）
- [ ] サーバログにエラースタックがない

**G2未達 → バインドアドレス・ポート・SSEパスを修正。フェーズ3へ進まない**

---

## フェーズ3：ネットワーク（パブリック到達）

### 3.1 作業（インフラ）

1. AWS SG: **TCP 待受ポート** を **自宅IP/32**（必要ならAID用は別ルール）に限定許可。
2. `ufw status` 等で OS 側ブロックがないか確認。ある場合は同ポート許可または無効化方針を決める。

### 3.2 確認（EC2上）

```bash
ss -tlnp | grep 8765
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8765/health
```

### 3.3 確認（自宅等クライアント）

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://<パブリックIP>:8765/health
```

### 3.4 サーバログ

- [ ] 自宅からのアクセス時、ログに **クライアント実IP** が残る（またはリバースプロキシの場合はX-Forwarded-For）

### ゲート G3

- [ ] EC2ローカルは成功のまま
- [ ] **パブリックIP経由のcurl** が成功（またはSSEが返る）
- [ ] 失敗時は SG → OSFW → リスンアドレス の順で疑う

**G3未達 → フェーズ4へ進まない**

---

## フェーズ4：Cursor MCP クライアント

### 4.1 作業

1. Cursor の MCP 設定に、**フルURL**（`http://<パブリックIP>:8765/<SSEパス>`）を登録。
2. Cursor 再起動または MCP 再読み込み。

### 4.2 確認

- [ ] ツール一覧に `get_employee_list` 等が表示される
- [ ] `get_employee_list` 実行で、仕様どおりのJSONに近い結果
- [ ] サーバログに該当ツール名・成功が残る

### 4.3 失敗時

- HTTPのみ拒否 → HTTPS ターミネーションを計画（フェーズ2〜3をHTTPS向けにやり直し）
- パス不一致 → 実装のSSE URLとCursor設定を**文字列完全一致**で修正

### ゲート G4

- [ ] 少なくとも1ツールがCursorから成功
- [ ] サーバ側に異常スタックなし

**G4未達でも AID 試験は可能だが、原因が「サーバ」か「Cursor」か切り分けが付かないため、G3まで正常なら記録のみ残し、必要なら並行してフェーズ5を検討**

---

## フェーズ5：AID 登録・スキャン（Feature 1）

### 5.1 作業

1. AID Management API で `POST /mcp/servers`（URLは **AIDから到達可能な** ホスト。パブリックIPまたはDNS）。
2. `POST /mcp/servers/scan` → `GET /mcp/servers/scan/{scan_id}` を**ポーリング**（仕様書セクション3）。

### 5.2 API応答の保存

- 各レスポンスをファイルに保存（例: `scan_register.json`, `scan_status_1.json`）。
- タイムアウト時は **最終応答本文** を残す。

### 5.3 ログ確認

- MCPサーバ: AID側のプローブで **接続ログ**が残るか
- AID: コンソールまたはAPIで **スキャン完了・結果**を確認

### ゲート G5

- [ ] 登録が完了し `server_id` がある
- [ ] スキャンが **完了状態** まで到達（失敗なら応答の `statusInfo` 等を確認）
- [ ] Tool Poisoning ツールに **何らかの検知**（重大度は **HIGH 非保証**。仕様書セクション2参照）

**G5未達 → AIDからのURL到達・認証・ファイアウォールを確認。クライアント側ログとAIDレスポースを突き合わせる**

---

## フェーズ6：Gateway URL → Dify（Feature 2）

### 6.1 作業

1. `POST /resource/connections`（`MCPGateway`, `resource_ids`）
2. `GET /connections/{connection_id}` で `proxy_url` 取得
3. Dify の MCP 接続先を **`proxy_url`** に設定
4. 同一プロンプトで **Before（直URL）/ After（Gateway）** の差を確認

### 6.2 ログ・証跡

- AID: ブロック・マスクのイベントがあればスクリーンショットまたはエクスポート保存
- MCPサーバ: ツール呼び出しの有無・エラー

### ゲート G6

- [ ] Dify から Gateway 経由でツール実行できる、または期待どおり Guardrail が作動
- [ ] 重大なサーバエラーなし

## 7. 巻き戻し・再試験

| 障害箇所 | 戻り先 |
|----------|--------|

| パブリックのみ失敗 | フェーズ3 |
| Cursorのみ失敗 | フェーズ4と3の再確認 |
| AID登録/スキャン失敗 | フェーズ3と5 |
| Difyのみ失敗 | フェーズ6と `proxy_url` |
